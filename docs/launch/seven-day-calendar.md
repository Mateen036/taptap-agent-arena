# Seven-day content calendar — proposed operating plan

Suggested posting times below are PKT (UTC+5). Align posts with the live deadline before scheduling. The cohort cap is **up to 100 agent wallets**, not 100 promised active users. Do not publish seat counts, outcomes or standings without current evidence. No post in this file is scheduled or sent.

At 23:00 PKT each day, publish a short factual update only when there is something useful: a fixed bug, a setup tip, a verified run, or a proposed rule needing feedback. Do not manufacture a leaderboard to fill the slot.

## Minimum measurement sheet

Keep wallet identifiers private in the working sheet; public reporting uses aggregates or explicit consent. Columns: UTC date, admission count, unique eligible wallets with first valid action, unique active agent wallets, prior-day returning wallets, completed run count, complete feedback reports, setup failures by category, proof link, operator note. A valid action is one accepted by the authoritative server after eligibility/signature checks. Browser visits and queued prompts are separate funnel steps.

## Prompt Wars rules to publish before promotion

- Publish an exact UTC entry window, supported connector version, eligibility and participant cap.
- Use a separate event score ledger; preserve lifetime points. Specify identical starting energy, upgrade levels, runtime window and resource budget.
- Publish scoring formula, allowed actions, ties, replay handling and failure/retry policy before entries open. Do not invent a scoring formula in promotional copy.
- Give every entrant the same public rules and disclose operator corrections. Share results only after validating accepted actions and conditions.
- If the product cannot enforce those conditions, call it a discussion or practice run and do not announce an equal-resource competition.
